(a) Schema — approve with two small redlines
The schema is genuinely well thought through. The three additions vs. my original sketch are all correct calls:

titleTemplate instead of title is the right move — the existing code interpolates runtime values like brand age, and pretending otherwise would force render logic into the JSON.
ExpectedLift as a discriminated union is much better than my flat number | null. The unit/range distinction ("30.3%" vs "3.2×" vs "43 positions" vs [35, 40]) is exactly the kind of thing that becomes painful if you punt on it.
aliases and retired are essentials for a long-lived data file — good catch.

Keeping trigger conditions out of the JSON is the right architectural call. The JSON describes what each rec means; the trigger code decides when it fires. Don't let those merge.
Two small redlines:
Redline 1 — Add an updatedAt field separate from lastVerifiedAt. lastVerifiedAt answers "when did a human confirm the source still says what we say it says?" but doesn't answer "when did this record itself last change?" The two diverge — you can fix a typo in the claim text without re-verifying the source. Add updatedAt: string (ISO date, required, auto-bumped on any change) so the methodology page can show both.
Redline 2 — Constrain ExpectedLift.range semantics. Right now range?: [number, number] is ambiguous. Is it a confidence interval? A reported min/max across studies? An A/B-test 95% CI? Pick one and document it in the type comment. My suggestion: range represents the source's reported range (e.g., the paper reports "30.3% on average, with individual prompts ranging 18–47%"). If you want CIs later, add a separate field. Otherwise the UI rendering will be inconsistent.
Otherwise: approved. The notes field staying out of the LLM prompt is exactly right — that's where the hedging and editorial context lives, and it shouldn't leak into customer-facing summaries.
(b) Migration plan — approved
The two architectural calls are both right.
File-only, no DB table is correct for now. This is reference data, edits go through code review, and there's no editor-driven workflow to support yet. Adding a DB table would just create two sources of truth. If you ever build a CMS-style editor for recs, the JSON becomes the seed and the table becomes the live store — that's a clean evolution.
Server-side enrichment, not client-side join is also correct. PDF export, future webhooks, and any non-web client all need the same enriched payload, and the API contract is the right place to formalize that. Not having to ship a recommendations bundle to the client is a small but real win.
The 4-commit sequence (lib → trigger refactor → API enrichment → UI) is clean. Reviewability is good. Steps 1–3 are invisible to users, which means you can ship them and validate the data path works before exposing badges in the UI.
One refinement: in step 3, when you add source to the API response, also add a top-level recommendationsSchemaVersion field on the audit response (e.g., "v1"). Old reports that lack source data will be undefined/null for the version field. This makes the "audit predates source tracking" UI fork explicit and queryable rather than inferred from missing fields.
